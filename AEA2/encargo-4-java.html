Encargo 4 · Aplicación Java

Desplegar el gestor de torneos y comprobar su colaboración con el portal PHP.

Equipos de tresDespliegue individualTomcat + MariaDB

Qué necesita Punto de Juego

Gestión interna de torneos

«Ya publicamos actividades y clasificaciones. Necesitamos consultar las rondas y registrar los resultados de las partidas presenciales desde una aplicación Java. El portal PHP debe reflejar esos cambios sin volver a introducirlos».

Recibís la aplicación cerrada en un WAR. No tenéis que programar Java: vuestra responsabilidad es preparar el entorno, configurar, desplegar y verificar.

Descargar aplicación Java · ZIP

Incluye tornejos.war, fuentes y requisitos. Consulta la teoría breve de Java y Tomcat y el README de la aplicación.

1. Tareas del equipo, realizadas en cada ordenador

Paso Qué debes hacer Resultado
Preparar Instalar JDK 17 o 21 y Tomcat 10.1. Identificar el Java del servicio, su configuración, directorio de despliegue y logs.
Crea el fichero de configuración. en /etc/tomcat10/Catalina/localhost/tornejos.xml :
<Context> <Environment name="jdbcUrl" value="jdbc:mariadb://127.0.0.1:3306/puntdejoc" type="java.lang.String" override="false"/> <Environment name="jdbcUser" value="USUARIO_JAVA" type="java.lang.String" override="false"/> <Environment name="jdbcPassword" value="CLAVE_USER" type="java.lang.String" override="false"/> </Context> 		Tomcat activo y accesible solo en el equipo local, puerto 8080.
Conectar Crear una cuenta Java con SELECT en puntdejoc y UPDATE únicamente de resultat en partides. Configurar jdbcUrl, jdbcUser y jdbcPassword como entradas JNDI externas al WAR. Java accede a la base existente sin utilizar root ni modificar la cuenta PHP.
Desplegar Publicar tornejos.war en Tomcat; comprobar contexto y registros. http://127.0.0.1:8080/tornejos/ muestra torneos, rondas y partidas.
Colaborar Incorporar el artefacto y los requisitos al repositorio común; anotar su versión. Conservar los secretos fuera de Git. Los tres integrantes despliegan la misma aplicación y conocen su configuración.

Apache, PHP-FPM y MariaDB se mantienen. No copiéis el WAR en la raíz de Apache. No es necesario desplegar la API Node.js ni configurar Apache como proxy.

2. Pruebas individuales

  1. Mostrar Tomcat activo, puerto local, versión Java del servicio y contexto de la aplicación.
  2. Consultar el torneo 2: tres rondas y seis partidas. Si ya modificaste datos en el encargo anterior, registra el estado inicial antes de probar.
  3. Con la partida 3 pendiente, comprobar Aina 3, Cris 1, Dani 1 y Biel 0 en PHP. Guardar desde Java una victoria del segundo jugador en esa partida y comprobar Cris 4 en PHP.
  4. Reiniciar Tomcat y comprobar que el resultado se conserva. Confirmar que Apache y el portal PHP siguen funcionando.
  5. Solicitar una ruta inexistente y relacionar el 404 con su registro de acceso. Detener MariaDB brevemente, observar el fallo controlado, localizarlo en los logs y recuperar el servicio.
  6. Comprobar que la cuenta Java puede cambiar el resultado y no puede borrar tablas. Verificar que WEB-INF y las credenciales no son descargables por HTTP.

La aplicación solo permite cambios en torneos en curso y desde el propio equipo. No genera emparejamientos ni incorpora login: es un prototipo local, no una herramienta lista para publicar.

3. Entrega

  • Repositorio compartido con WAR y README actualizado, sin credenciales.
  • Markdown individual con versiones, diagrama de servicios, configuración anonimizada, procedimiento, pruebas e incidencia resuelta.
  • Aplicación funcionando en tu ordenador y explicación del recorrido Tomcat → JDBC → MariaDB y del cambio observado en PHP.

Criterios principales: RA1 1.4, 1.6, 1.7, 1.8 y 1.9. Se valora desplegar, comprobar y justificar, no reprogramar la aplicación.

Si terminas antes: comprueba que un torneo sin rondas muestra una respuesta adecuada, prueba una URL con otro contexto o mejora el README tras una revisión cruzada. No cambies el esquema compartido ni introduzcas nuevas funciones.
