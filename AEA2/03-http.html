1. Interpretar una URL

En el lenguaje cotidiano, a una URL se le llama «dirección web» o «dirección del enlace». Cuando copias un enlace y lo pegas en un mensaje, el texto que pegas es una URL. En plural se suele escribir URLs.

Recuerda

Una URL es una dirección, no el recurso en sí. Una misma página puede ser accesible mediante varias URLs: con y sin www, con etiquetas de seguimiento o a través de un enlace corto. Esto depende de cómo esté configurado el sitio; las direcciones no son equivalentes automáticamente.

Una misma URL puede mostrar contenido distinto con el tiempo si quien administra el sitio modifica la página.

Las partes de una URL

Imagina que Punto de Juego permite consultar torneos y filtrar las actividades de Mataró. Una dirección podría tener esta forma:

https://torneos.puntodejuego.example:8443/torneos/ajedrez?municipio=mataro&categoria=juvenil#clasificacion

Es un ejemplo didáctico, no una web que debas visitar: .example se reserva para ejemplos. La dirección reúne todas las partes que vamos a estudiar; la mayoría de las URLs solo utilizan algunas.

Parte En el ejemplo Qué hace ¿Obligatoria?
Esquema https:// Indica cómo se obtiene el recurso. El esquema es https y :// lo separa del host. HTTPS utiliza HTTP protegido mediante TLS, encriptado. Otros esquemas son http:, mailto:, tel: y file:; no todos usan //. Sí, en una URL absoluta. Un enlace relativo puede omitirlo y tomarlo de la página que lo contiene.
Subdominio torneos. Prefijo opcional que permite organizar servicios o secciones. Aquí identifica la sección de torneos. www es otro ejemplo habitual. No.
Nombre de dominio puntodejuego Junto con el TLD forma el dominio base del ejemplo: puntodejuego.example. No si usamos una IP o un nombre local como localhost.
Dominio de nivel superior (TLD) .example Última etiqueta del nombre del host. En este caso está reservada para documentación. Otros TLD son .com, .org y los de código de país, como .es, .uk o .ai (Anguila). Forma parte de un nombre de dominio completo; no se utiliza en una IP ni es necesario con localhost.
Puerto :8443 Identifica el puerto de red al que se conecta el navegador. Los valores predeterminados son 443 para HTTPS y 80 para HTTP. No si usamos el predeterminado. Sí debe indicarse si el servicio escucha en otro puerto, como 8443.
Ruta /torneos/ajedrez Identifica el recurso solicitado: aquí, los torneos de ajedrez. Puede parecer una estructura de carpetas, pero no tiene que coincidir con directorios o archivos físicos. Puede omitirse; para HTTP(S) se utiliza / como ruta inicial.
Cadena de consulta (query string) ?municipio=mataro&categoria=juvenil Proporciona parámetros, habitualmente pares clave=valor separados por &. Aquí propone dos filtros: municipio y categoría. La aplicación debe estar preparada para interpretarlos. No.
Fragmento (ancla) #clasificacion Identifica una sección de la página, si existe el ancla correspondiente. Lo gestiona el navegador y no se envía al servidor en la petición HTTP. No.

Cómo leer el ejemplo de Punto de Juego

«Conecta mediante HTTPS al host torneos.puntodejuego.example, en el puerto 8443; solicita /torneos/ajedrez e incluye los parámetros municipio=mataro y categoria=juvenil. Al recibir la página, sitúate en su sección clasificacion».

El host completo incluye el subdominio y el dominio base. Escribir un filtro o un fragmento no crea esa funcionalidad: el servidor debe admitir el filtro y el documento debe tener la sección de destino.

¿Y cuando trabajamos en nuestro ordenador?

En el despliegue local también usamos URLs:

http://localhost/portal/torneig.html
http://127.0.0.1:8000/torneig.html

La primera podría corresponder a Apache HTTP Server en el puerto 80 si hemos publicado el portal bajo /portal/. La segunda correspondería a un servidor de pruebas escuchando en 8000 y sirviendo directamente esa carpeta. La ruta concreta depende de vuestra configuración.

127.0.0.1 es una dirección de loopback: apunta al propio equipo. localhost es un nombre que normalmente resuelve a loopback. Una IP literal no necesita consultar DNS para localizar ese host. Por eso una URL web puede funcionar sin un dominio público ni un TLD.

Referencia: MDN · Qué es una URL y cuáles son sus partes.

2. ¿Qué es una petición HTTP?

Una petición HTTP es el mensaje que un cliente, como el navegador, envía a un servidor para solicitar un recurso o pedir que se procese una acción. El servidor la interpreta y devuelve una respuesta.

En Punto de Juego, abrir el catálogo implica solicitar su página. Más adelante, guardar un resultado supondrá enviar datos para que la aplicación los procese. El método de la petición indica qué operación se solicita; el estado de la respuesta comunica qué ha ocurrido. Son conceptos diferentes.

Una página puede generar varias peticiones

El navegador suele solicitar primero el documento HTML. Al interpretarlo, descubre otros recursos que necesita y puede pedir el CSS, las imágenes y los scripts. Si la aplicación consulta datos mediante JavaScript, también pueden aparecer peticiones a una API.

El HTML responde 200

El navegador recibe la estructura de la página y puede mostrar su contenido.

El CSS responde 404

El recurso de estilos no se encuentra. La página puede verse sin diseño aunque el HTML se haya descargado correctamente.

No siempre se descargan todos los recursos de nuevo: el navegador puede reutilizar su caché. Tampoco existe un número fijo de peticiones por página.

Qué contiene una petición

GET /portal/torneig.html HTTP/1.1
Host: localhost
Accept: text/html
  • Método: GET, la operación solicitada.
  • Destino: /portal/torneig.html, la ruta. Puede incluir parámetros de consulta; el fragmento #... no se envía.
  • Versión: HTTP/1.1 en este ejemplo.
  • Cabeceras: información adicional, como el host solicitado y el tipo de contenido que el cliente acepta.
  • Cuerpo: datos enviados cuando la operación los necesita. Los GET y HEAD de nuestros ejemplos no llevan cuerpo.

La representación anterior corresponde a HTTP/1.1. Las herramientas del navegador permiten observar estos conceptos aunque la comunicación use otra versión de HTTP.

2.1Peticiones GET y HEAD

GET · Obtener el recurso

Solicita una representación del recurso. Si la petición tiene éxito y la respuesta incluye contenido, podemos recibir el HTML, el CSS, una imagen o datos.

HEAD · Consultar sin descargar el cuerpo

Solicita una respuesta como la de GET, pero sin su cuerpo. Permite consultar estado y metadatos del recurso.

Con HEAD puedes consultar, por ejemplo, el tipo de contenido y, si el servidor lo proporciona, el tamaño mediante Content-Length. Algunos metadatos pueden omitirse. Una respuesta HEAD sin cuerpo no significa que el archivo esté vacío.

GET y HEAD se utilizan para consultar: no deberían emplearse para registrar una inscripción o modificar resultados. Que el servidor registre la visita en un log no cambia el propósito de la operación.

Comparar los dos métodos

Si tu Apache publica el portal bajo /portal/, puedes observar la diferencia con estas peticiones al mismo recurso. Adapta la URL a tu despliegue:

# GET: muestra las cabeceras y el cuerpo de la respuesta.
curl -i http://localhost/portal/torneig.html

# HEAD: muestra las cabeceras; no descarga el cuerpo.
curl -I http://localhost/portal/torneig.html

-i es una i minúscula; -I es una i mayúscula. Son opciones distintas. Una ejecución normal de curl obtiene el recurso indicado: no carga automáticamente el CSS y las imágenes como hace un navegador al representar una página.

Más adelante

Trabajaremos POST, PUT, PATCH, DELETE y OPTIONS cuando las funcionalidades de la aplicación lo requieran. Ahora nos centramos en GET y HEAD para comprobar el despliegue de la web estática.

Referencia de los métodos: GET y HEAD en RFC 9110.

2.2Respuestas HTTP

La respuesta HTTP es el mensaje que devuelve un servidor tras recibir una petición. Incluye un estado, cabeceras y, cuando corresponde, un cuerpo.

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 67

<!doctype html><html lang="es"><title>Punto de Juego</title></html>

Este ejemplo simplificado muestra una respuesta con HTML. La versión, las cabeceras y su orden pueden variar. No todas las respuestas tienen cuerpo: HEAD y 304 son dos casos que encontrarás en las pruebas.

Cómo interpretar las cabeceras

Cabecera Qué observar
Content-Type Tipo del contenido: por ejemplo, text/html, text/css o application/json.
Content-Length Tamaño del cuerpo en bytes cuando se indica. En HEAD puede describir el que se enviaría con GET.
Location Dirección de destino cuando se comunica una redirección.
Cache-Control, ETag, Last-Modified Información que puede intervenir en la conservación y validación de copias en caché.
Server Puede identificar software del servidor, pero puede ocultarse o modificarse. No demuestra por sí sola qué servicio responde.

Familias de códigos de estado

El primer dígito orienta la interpretación: 1xx informativos, 2xx éxito, 3xx redirección o uso de caché, 4xx problema con la solicitud o el acceso, y 5xx fallo del servidor o de sus servicios de apoyo.

Código Significado Ejemplo o comprobación
200 OK La petición se ha atendido correctamente. El portal responde; revisa también que el contenido sea el esperado.
301 / 302 Redirección permanente / temporal. Comprueba Location y el destino. No son errores por sí mismos.
304 Not Modified El cliente puede reutilizar una copia validada. Puede aparecer al recargar con caché; no es un fallo de descarga.
403 Forbidden El servidor rechaza el acceso. Comprueba permisos, reglas de acceso y configuración; el código no identifica por sí solo la causa.
404 Not Found No se encuentra el recurso solicitado. Revisa URL, mayúsculas y ubicación del archivo.
405 Method Not Allowed El recurso no admite ese método. Comprueba qué operación se ha enviado y qué admite el servicio.
500 Internal Server Error El servidor encuentra un fallo interno. Consulta sus registros y, si existe, los de la aplicación.
502 / 503 Fallo de un servidor intermediario / servicio no disponible. Investiga los componentes implicados y sus logs; los estudiaremos con la integración de servicios.

Idea clave

Un error HTTP implica que algún servidor ha respondido. Un fallo de resolución DNS, una conexión rechazada o un tiempo de espera agotado pueden impedir recibir respuesta HTTP. No deben etiquetarse automáticamente como 404 o 500.

Referencia: códigos de estado HTTP en MDN.

3. Observar y diagnosticar

No basta con comprobar que la página «se ve». Debes relacionar lo que observa el navegador con el servicio y los archivos que has desplegado. Trabaja sobre la URL real de tu Apache HTTP Server.

Los ejemplos usan http://localhost/portal/: esta ruta solo funcionará si has publicado ahí el portal. Si lo sirves en la raíz, utiliza http://localhost/. No cambies el despliegue solo para copiar una URL del apunte.

3.1Sigue las peticiones con el navegador

  1. Abre las herramientas de desarrollo y selecciona Red / Network antes de recargar.
  2. Desactiva temporalmente la caché con las herramientas abiertas. Activa «conservar registro» si necesitas seguir una redirección.
  3. Recarga y localiza el documento HTML. Anota URL, método, estado y tipo de contenido.
  4. Abre Headers / Cabeceras: separa lo enviado en la petición de lo recibido en la respuesta.
  5. Revisa Response / Respuesta y, cuando exista, Preview / Vista previa. Comprueba si el HTML pertenece realmente a Punto de Juego.
  6. Localiza el CSS y las imágenes. Compara sus estados. Si no existe un tipo de recurso en tu portal, no tienes que inventar una petición.
  7. Observa Initiator / Iniciador y el tiempo de carga para relacionar cada recurso con quien lo solicita. El detalle depende del navegador.

Que el HTML devuelva 200 no demuestra que todas las imágenes funcionen. Una página predeterminada de Apache también puede devolver 200 sin ser tu proyecto.

3.2Aísla una petición con curl

Estas comprobaciones permiten comparar una descarga GET, una consulta HEAD y un recurso que no existe: 

curl --max-time 5 -i http://localhost/portal/
curl --max-time 5 -I http://localhost/portal/style.css
curl --max-time 5 -i http://localhost/portal/recurso-inexistente.html

--max-time 5 limita la prueba a cinco segundos. Para observar el establecimiento de la conexión puedes usar curl -v; para seguir redirecciones, curl -L. Primero mira la respuesta inicial: seguirlas puede ocultar el paso que intentas diagnosticar.

Compara método, estado, cabeceras y cuerpo. El código de salida de curl no es el estado HTTP: sin opciones adicionales, curl puede terminar correctamente aunque haya recibido un 404.

Referencia: manual oficial de curl.

3.3Relaciona las pruebas con Apache

Consulta el estado del servicio, identifica el proceso que escucha el puerto utilizado y revisa los registros. Emplea los nombres y rutas de tu instalación.

Ubuntu

Habitualmente: servicio apache2 y registros bajo /var/log/apache2/.

Fedora

Habitualmente: servicio httpd y registros bajo /var/log/httpd/.

  • Access log: busca una petición por su hora, ruta, método y estado. Su formato depende de la configuración.
  • Error log: busca información sobre fallos o restricciones. No todos los estados generan una entrada aquí.
  • Configuración y archivos: relaciona la URL con la raíz documental o el sitio configurado y comprueba permisos sin aplicar cambios globales a ciegas.

Una respuesta puede venir de otro servidor o de un intermediario. Relaciona servicio, puerto, configuración y registro para demostrar que estás comprobando tu Apache. No desactives el cortafuegos, SELinux o los controles de acceso para intentar arreglar un síntoma sin diagnóstico.

Referencia: registros de Apache HTTP Server.

3.4Sigue un orden de diagnóstico

URL y destino→Conexión y servicio→Respuesta HTTP→Recurso y logs
Qué observas Qué puede indicar Siguiente comprobación
No se resuelve el nombre. Nombre mal escrito o problema de resolución. No hay respuesta HTTP. Revisa host y resolución. No cambies HTML.
Connection refused. No hay un servicio aceptando la conexión en ese destino o se rechaza activamente. Comprueba IP, puerto, escucha y estado del proceso.
Tiempo de espera agotado. El destino o la comunicación no responden dentro del plazo. Revisa conectividad, filtros y servicio; no deduzcas un código HTTP.
Error TLS con HTTPS. Negociación o certificado no válidos para ese acceso. Comprueba esquema, nombre y configuración HTTPS. HTTP y HTTPS no son intercambiables.
200, pero aparece otra página. Otro sitio, raíz documental o servidor está respondiendo. Relaciona URL, configuración, contenido y logs.
HTML 200, CSS 404. El estilo se pide en una ruta inexistente. Revisa href, ruta relativa y mayúsculas.
403. Acceso denegado por alguna regla o condición. Consulta configuración, permisos y registros.
404. Recurso no encontrado en ese destino. Comprueba URL y mapeo al archivo o a la aplicación.
Listado de un directorio. Puede faltar el índice esperado y estar permitido el listado. Revisa el contenido y la configuración del directorio publicado.
No ves el último cambio. Puede haber caché o una copia de despliegue desactualizada. Compara archivo servido, archivo del repositorio y respuesta con caché desactivada.

3.5Comprueba y documenta

Aplicación a Punto de Juego

  1. Obtén una respuesta correcta del portal y otra de su CSS. Explica qué recurso verifica cada prueba.
  2. Compara GET y HEAD sobre el mismo recurso, identificando qué cambia.
  3. Pide una ruta inexistente y relaciona su 404 con la entrada del registro de acceso.
  4. En una copia de pruebas, modifica temporalmente el enlace al CSS. Predice qué ocurrirá, compruébalo y restaura la ruta. Conserva la prueba de recuperación.
  5. Relaciona las observaciones con el servicio Apache y la ubicación publicada. Si el síntoma no coincide con tu hipótesis, revísala antes de modificar otra cosa.

En tu Markdown indica objetivo, entorno, URL, método, resultado esperado, resultado observado y conclusión. Una captura debe permitir identificar el recurso y su estado; acompáñala de una explicación.

Ampliación opcional

Una hipótesis, una prueba

Compara la carga con caché activada y desactivada, sigue una redirección que exista en tu entorno o investiga un error reproducible. Documenta la hipótesis, las observaciones y la conclusión. No necesitas provocar errores en servicios de otras personas.

Comprueba que lo entiendes

  1. ¿Por qué puede responder 200 el HTML y verse la página sin diseño?
  2. ¿Qué diferencia hay entre el método HEAD y el estado 304?
  3. ¿Por qué una conexión rechazada no es un 404?
  4. ¿Qué pruebas demuestran que responde tu Apache y no otro servicio?
  5. ¿Por qué una URL file:// no sirve para observar la respuesta HTTP del documento?

Al abrir un archivo con file://, el navegador lee el documento del disco. Para estas pruebas debes acceder mediante http:// o https:// a un servicio configurado. Si usas una herramienta de comprobación externa, recuerda que no puede acceder a tu localhost.
