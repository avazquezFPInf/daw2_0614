Encargo 1 · Página estática

Primera entrega: Punto de Juego necesita una web de presentación publicada con Apache HTTP Server.

Entrega 1Apache HTTP ServerEvidencias en Markdown

La primera necesidad del cliente

«Antes de gestionar inscripciones y torneos, queremos que la gente nos encuentre y conozca nuestras actividades. Necesitamos una primera web de Punto de Juego con presentación, encuentros y un torneo de ejemplo».

Recibís un portal HTML/CSS mínimo para personalizarlo y desplegarlo. Los resultados del torneo son una demostración estática: no hay formularios funcionales ni almacenamiento en base de datos.

Descargar la página web estática · ZIP

Resultado que debéis conseguir

Un repositorio compartido por los tres miembros y tres despliegues individuales del mismo portal, uno en cada ordenador, servidos por Apache HTTP Server.

Abrir index.html desde el disco no acredita el despliegue. Un servidor de demostración de Python tampoco sustituye Apache HTTP Server en esta entrega.

1 · Reconocer y organizar los archivos

  1. Descargad el ZIP e identificad la función de cada archivo antes de modificarlo.
  2. Organizad el proyecto con una carpeta para el portal y otra para la documentación.
  3. Explicad qué recursos necesita esta versión y cuáles todavía no necesita: no instaléis PHP ni MariaDB para una web estática.

2 · Crear el Git de trabajo compartido

  1. Cread un repositorio de equipo en GitHub e incorporad los archivos del portal.
  2. Añadid a los tres miembros como colaboradores y comprobad sus accesos.
  3. Cada integrante clona el repositorio y trabaja con su identidad de autoría.
  4. Acordad cómo repartir cambios y sincronizar el trabajo. Conservad commits pequeños y explicativos.
  5. Redactad un README común con descripción, integrantes, estructura e instrucciones de despliegue.
  6. Elegid un mimebro del equipo apra que sea el capitan, este deberá enviar un mail a la profesora con la información de los mimebros del equipo y enlace al git.

Recuperad los procedimientos de AEA1. No creéis repositorios anidados ni subáis archivos que contengan credenciales.

3 · Personalizar la presencia de Punto de Juego

  1. Adaptad la marca visible a Punto de Juego y explicad su origen en Mataró y su expansión al Maresme.
  2. Elegid juegos y preparad actividades ficticias con información coherente.
  3. Personalizad la presentación visual manteniendo una web sencilla, legible y navegable.
  4. Verificad enlaces y recursos. Compartid los cambios para que las tres copias tengan la misma versión.

Identificad claramente los resultados de demostración. No añadáis botones de inscripción que aparenten funcionar si no existe esa funcionalidad.

4 · Instalar y preparar Apache HTTP Server en cada equipo

En este encargo utilizamos Apache HTTP Server, el servidor web. No se instala Apache Tomcat, que incorporaremos cuando despleguemos la aplicación Java.

Consulta la página oficial de Apache HTTP Server. Sus archivos de descarga incluyen el código fuente; para esta práctica en Ubuntu instalaremos el paquete apache2 desde los repositorios de la distribución, sin compilarlo manualmente. En Fedora el paquete y el servicio se denominan httpd.

Referencia de instalación: documentación oficial de Ubuntu. Identifica y documenta los pasos que correspondan a tu sistema.

  1. Identificad vuestra distribución y comprobad si Apache HTTP Server ya está instalado o si otro proceso ocupa el puerto HTTP.
  2. Consultad documentación de vuestra distribución e instalad el servidor web si es necesario.
  3. Identificad nombre del servicio, archivos de configuración, raíz documental y registros. Ubuntu y Fedora pueden usar nombres y rutas diferentes.
  4. Iniciad el servicio y comprobad su estado y la respuesta HTTP.
  5. Desplegad el portal en una ubicación servida por Apache HTTP Server, conservando los archivos del repositorio como copia de trabajo.
  6. Revisad permisos de lectura y acceso a directorios. Si Fedora utiliza SELinux, tened en cuenta sus contextos: no desactivéis mecanismos de protección para resolver la práctica.
  7. Comprobad el portal mediante una URL HTTP de vuestro propio ordenador e identificad qué ruta del disco se está sirviendo.

La entrega mínima se verifica desde el propio equipo. El acceso desde otros equipos no es obligatorio y no requiere abrir servicios al exterior.

Documentad las decisiones y los comandos que realmente habéis utilizado, con una explicación breve de su función. No se pide copiar una receta única.

5 · Verificar el despliegue y resolver incidencias

  1. Recorred las páginas y comprobad que el contenido y el CSS se sirven correctamente.
  2. Inspeccionad una petición del documento y otra de un recurso: anotad URL, estado y tipo de contenido.
  3. Solicitad una ruta inexistente y explicad la respuesta. Consultad el registro de Apache HTTP Server relacionado con una petición de vuestra prueba.
  4. Comprobad que está respondiendo vuestro Apache HTTP Server: relacionad servicio, configuración, ubicación de archivos y logs. No os baséis solo en una cabecera.
  5. Reiniciad el servicio de forma controlada y verificad que el portal vuelve a responder.
  6. Registrad una incidencia, real o provocada de forma reversible, con diagnóstico, solución y prueba de recuperación.

Qué debéis entregar

Entrega de equipo Evidencia individual
URL del repositorio, código personalizado y README reproducible. Documento Markdown propio con sistema y versiones, instalación, configuración, ubicación del portal y URL local.
Historial con aportaciones de los tres miembros. Pruebas de Apache HTTP Server, páginas, recursos, error controlado, logs y recuperación.
Versión común identificada para la entrega. Aplicación funcionando en el ordenador del alumno y capacidad para explicarla.

No incluyáis únicamente capturas. Relacionad cada prueba con el resultado que demuestra. No es necesario entregar una copia de todos los archivos del sistema.

Encargo conseguido

Cualquier integrante puede mostrar su portal servido por Apache HTTP Server y explicar cómo otro compañero puede reproducirlo siguiendo la documentación.

Criterios principales: 1.2, 1.3, 1.6, 1.7, 1.8 y 1.9.

Si termináis antes

Elegid una mejora acotada y verificable:

  • Revisar accesibilidad con teclado, foco y estructura de títulos.
  • Mejorar la vista móvil y corregir desbordamientos.
  • Añadir una página de reglas o una actividad manteniendo la navegación.
  • Integrar una mejora mediante pull request revisada.
  • Intercambiar documentación con otro equipo y registrar qué pasos faltaban para reproducirla.

Documentad el antes, el cambio y su comprobación. No incorporéis nuevas tecnologías solo para ampliar la entrega.
