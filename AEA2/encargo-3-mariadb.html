Encargo 3 · Datos y clasificación

Punto de Juego necesita conservar sus torneos y publicar una clasificación que responda a los resultados registrados.

Equipos de tresDespliegue individualApache + PHP-FPM + MariaDB

El encargo de la asociación

Punto de Juego · Mataró

«Tenemos actividades y torneos presenciales. Queremos publicar cuáles están disponibles y consultar la clasificación de un torneo de demostración. Los resultados se registrarán después de jugar: no queremos un juego online. La información debe conservarse cuando reiniciemos el servidor y actualizarse sin modificar el código del portal».

Recibís un prototipo PHP cerrado y un modelo de datos. Vuestro trabajo es desplegarlo, preparar la base con el SQL de apoyo, configurar la conexión y demostrar su funcionamiento. Podéis mantener vuestra identidad visual.

Descargar prototipo y modelo · ZIP

Descargar creación y datos iniciales · Markdown

Consulta la teoría de persistencia y bases de datos y el modelo relacional completo · Markdown. El ZIP también incluye el modelo; no contiene la solución SQL ni credenciales. En este encargo trabajamos con PHP y MariaDB. La API JavaScript queda para una próxima actividad; no debéis desplegarla ahora.

1. Organizar el trabajo y reconocer las piezas

  1. Integrad la nueva versión en vuestro repositorio común. Conservad identificables las entregas anteriores.
  2. Leed README y MODEL-DADES.md. Localizad carpeta pública, conexión, consultas y cálculo del ranking.
  3. Repartid revisión del SQL, despliegue y pruebas; revisad juntos el resultado. Rotad la revisión para que todos puedan explicar cada parte.
  4. Cada integrante debe instalar y configurar su propio servidor, base, cuenta y aplicación. Compartir código no sustituye las pruebas individuales.

Condición de partida: Apache y PHP-FPM ya funcionan. XAMPP permanece detenido. Documentad versiones y no mezcléis instancias.

2. Preparar el servidor de datos

  1. Identificad los requisitos, consultad documentación oficial e instalad MariaDB Server y su cliente utilizando los paquetes de vuestra distribución.
  2. Arrancad el servicio y configurad su inicio automático. Identificad configuración, puerto, almacenamiento y registros sin mover ni borrar los datos.
  3. Comprobad la escucha local y el acceso administrativo.
  4. Instalad pdo_mysql para la versión de PHP-FPM que sirve el portal. Reiniciad FPM y verificad la extensión en el contexto web.
  5. Documentad qué función tiene cada paquete. No es necesario instalar phpMyAdmin.

3. Construir el modelo relacional

La base se llamará puntdejoc, con codificación utf8mb4. Conservad los identificadores del modelo: el programa los utiliza.

TablaCampos y restricciones del modelo
jocsid INT PK; nom VARCHAR(100) único.
activitatsid INT PK; joc_id INT FK → jocs.id; titol VARCHAR(150); tipus ENUM(trobada, torneig); estat ENUM(borrador, oberta, en_curs, finalitzada); data DATE; lloc VARCHAR(150); places INT > 0.
inscripcionsid INT PK; activitat_id INT FK → activitats.id; alias VARCHAR(60); UNIQUE(activitat_id, alias).
rondesid INT PK; activitat_id INT FK → activitats.id; numero INT > 0; UNIQUE(activitat_id, numero).
partidesid INT PK; ronda_id INT FK → rondes.id; participant_a y participant_b INT FK → inscripcions.id; resultat ENUM(A, B, E) admite NULL; participant_a distinto de participant_b.

Todos los campos salvo resultat son NOT NULL. Usad IDs explícitos y no borrado en cascada. El modelo completo especifica también los datos iniciales. Disponéis de un Markdown con las sentencias de creación y carga. Revisadlas y relacionadlas con este modelo antes de ejecutarlas.

  1. Guardad en sql/01-esquema.sql las sentencias de creación proporcionadas. Revisad las cinco tablas, sus claves y restricciones y justificad el orden de creación.
  2. Guardad en sql/02-datos.sql las sentencias de carga proporcionadas y comprobad qué registros insertan. Los IDs proporcionados son parte del contrato del prototipo: el ranking utiliza el torneo 2.
  3. Escribid sql/03-consultas.sql: actividades abiertas con su juego, participantes del torneo 2, partidas pendientes con ronda y alias de ambos jugadores, y un UPDATE de una partida concreta.
  4. Ejecutad las sentencias en cada máquina y verificadlas con SELECT. Separad creación de esquema, carga y pruebas; explicad cómo repetir el proceso en una base vacía sin duplicar datos.
  5. Probad que se rechazan una referencia inexistente, plazas no positivas, un alias duplicado dentro de la misma actividad y una partida contra uno mismo. Conservad el error y su explicación.

Los intentos de datos inválidos son pruebas controladas: no desactivéis restricciones para hacerlos entrar. La cuenta usada para preparar el esquema es distinta de la cuenta de lectura del portal.

4. Configurar el acceso y desplegar

  1. Cread una cuenta de aplicación limitada a SELECT en esta base y al origen local elegido. Usad una contraseña propia por ordenador.
  2. Verificad sus permisos desde el cliente SQL utilizando la misma IP y cuenta que PHP.
  3. Desplegad el proyecto completo fuera de la carpeta pública y publicad únicamente public/. Elegid y justificad la publicación en Apache, conservando la integración con PHP-FPM.
  4. Configurad DB_HOST, DB_PORT, DB_USER y DB_PASSWORD en el pool FPM que atiende la aplicación. No basta con hacer export en una terminal.
  5. Mantened ALLOW_LAB_WRITE=0: en esta entrega los cambios se realizan por SQL; el formulario no es obligatorio.
  6. Comprobad configuración, reiniciad o recargad los servicios necesarios y abrid el portal por HTTP.

No subáis contraseñas, archivos del sistema con secretos ni copias con datos privados. Documentad parámetros y procedimiento usando marcadores en lugar de valores secretos.

5. Demostrar que funciona

Prueba individualResultado verificable

Realiza las pruebas en orden: la clasificación inicial se comprueba antes de cambiar la partida 3. Aporta resultado esperado, resultado obtenido y explicación, no solo capturas.

Entrega y evaluación

  • Repositorio compartido: versión del portal, scripts SQL de creación y carga proporcionados, consultas y pruebas elaboradas por el equipo, README con requisitos, estructura y despliegue sin secretos; contribuciones identificables.
  • Documento Markdown individual: entorno, diagrama de servicios, configuración, procedimiento reproducible, pruebas de la tabla anterior, incidencias y fuentes.
  • Demostración individual: aplicación funcionando en tu ordenador y explicación de una modificación SQL que se refleja en la web.

Debes poder explicar quién envía SQL, qué diferencia hay entre cliente y servidor MariaDB, qué permisos usa PHP y por qué el ranking se conserva tras reiniciar.

Se valorará funcionamiento, comprensión de la arquitectura, configuración justificada, pruebas y documentación. Aporta evidencias principalmente para los criterios RA1 1.1, 1.6, 1.7, 1.8 y 1.9; no sustituye las prácticas de Tomcat o virtualización.

Encargo conseguido

Cualquier integrante puede reproducir el despliegue, justificar la conexión entre servicios y demostrar que cambiar un dato cambia la respuesta sin editar PHP.

Si terminas antes: elige un reto

  • Consultas: diseña un JOIN que muestre todas las partidas con actividad, ronda y ambos alias. Explica por qué necesitas dos referencias a inscripcions.
  • Recuperación: realiza una copia lógica de la base y restáurala en otra base de prueba. Verifica recuentos y un resultado; no sobrescribas la original.
  • Integridad: demuestra qué ocurre al usar un participante de otra actividad. Propón cómo garantizar esa regla sin afirmar que la FK actual ya lo hace.
  • Auditoría cruzada: otro equipo sigue vuestro README en un entorno limpio o base nueva y registra qué paso falta.
  • Presentación: mejora la vista móvil de la clasificación y explica sus reglas de empate. Conserva el escapado y el funcionamiento.

Documenta objetivo, procedimiento y resultado de la ampliación. El formulario de escritura y la generación automática de rondas quedan fuera del encargo obligatorio.
