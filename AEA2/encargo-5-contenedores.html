Encargo 5 · Despliegue en contenedores

Reproducir los servicios de Punto de Juego y comprobar qué cambia al ejecutarlos con Docker.

Equipos de tresDespliegue individualCuatro servicios

La necesidad

Repetir el despliegue

«El portal y la gestión ya funcionan. Queremos preparar un entorno que podamos recrear en otros equipos y trasladar después a un servidor, con versiones, conexiones y almacenamiento definidos».

Trabajad por fases: primero Apache y la web estática; después web, PHP y datos; finalmente Java. No necesitáis terminarlo todo en la primera clase. Conservad el despliegue nativo para comparar.

Descargar laboratorio completo · ZIP

Incluye código, WAR, SQL inicial y configuración. Leed la teoría de contenedores y el README del laboratorio. No programaréis nuevas funciones ni desplegaréis la API.

1. Instalar Docker Engine, Compose y Portainer

Partimos de un ordenador con Ubuntu 24.04 LTS sin Docker instalado. Instalaremos Docker Engine, el plugin Compose y la interfaz web Portainer directamente en Ubuntu, sin Docker Desktop ni máquinas virtuales.

Descargar intalacionDockerCompose.sh

Guarda el fichero y ábrelo en el editor antes de ejecutarlo. Los comentarios explican cada bloque: herramientas necesarias, clave de firma, repositorio oficial, paquetes, arranque del servicio e instalación de Portainer.

Abre una terminal en la carpeta donde lo has guardado y ejecuta:

sudo bash intalacionDockerCompose.sh

El script necesita conexión a Internet y permisos de administración. Instala los paquetes desde el repositorio oficial de Docker y deja el servicio iniciado y preparado para arrancar al encender el ordenador. Si un comando falla, el script se detiene.

Primer acceso a la interfaz gráfica

  1. Abre https://localhost:9443 en el navegador de tu ordenador. El primer arranque puede tardar unos segundos.
  2. Portainer genera un certificado autofirmado: para esta dirección local, abre las opciones avanzadas del aviso del navegador y continúa.
  3. Crea tu cuenta de administrador con una contraseña propia. No la incluyas en el repositorio ni en las capturas.
  4. Entra en el entorno Docker local (puede aparecer como local o mediante Get Started). Localiza Containers, Images, Networks y Volumes. Los nombres pueden variar según la versión.

Si has dejado pasar el plazo del primer acceso y Portainer bloquea la configuración inicial, ejecuta sudo docker restart portainer y vuelve a abrir la página.

Portainer administra el mismo Docker Engine que usamos desde la terminal. No crea otra máquina virtual. Su contenedor es una herramienta de administración, adicional a los cuatro servicios del proyecto. Tiene acceso al motor mediante su socket; por eso limitamos la interfaz a este ordenador.

Si ya ejecutaste el instalador antes de que incluyera Portainer, ejecuta solo el bloque 6 del fichero actualizado con sudo delante de sus dos comandos docker. No repitas todo el script.

Crearemos el primer contenedor con el comando pautado y el entorno completo con Compose. Después utilizaremos Portainer para observarlos y administrarlos. Cuando usemos la terminal, será con sudo docker; no es necesario añadir vuestra cuenta al grupo docker.

Este script es para Ubuntu. Quienes utilicéis Fedora debéis seguir su procedimiento específico. Referencia: instalación oficial de Docker Engine en Ubuntu e instalación oficial de Portainer CE.

2. Primer contenedor: la web estática

Descomprime el ZIP y abre una terminal en su carpeta, donde están compose.yaml y estatica/. Para comparar el mismo portal, coloca en estatica/ una copia de vuestra web estática ya personalizada, con sus páginas, estilos, imágenes y demás recursos, conservando sus rutas relativas. Mantén también la versión del Apache nativo. Asegúrate de que 8081 está libre.

sudo docker run -d --name aea2-apache -p 127.0.0.1:8081:80 --mount type=bind,source="$(pwd)/estatica",target=/usr/local/apache2/htdocs,readonly httpd:2.4
sudo docker ps
sudo docker logs aea2-apache

En Portainer, abre Containers → aea2-apache. Identifica el estado, la imagen httpd:2.4, el puerto publicado y el montaje de la carpeta. Abre Logs para ver las peticiones que genera el navegador.

Comprobar que funciona como antes

No basta con ver la página de inicio. Abre vuestra web en el Apache nativo y en http://127.0.0.1:8081/ y recorre las mismas páginas en ambos despliegues. Utiliza la dirección habitual de la instalación nativa, incluida su subcarpeta si la tiene.

  • Contenido y aspecto: se mantienen los textos, la personalización, los estilos y las imágenes.
  • Navegación: funcionan los enlaces del menú, las páginas interiores y la vuelta al inicio. Comprueba que los enlaces del contenedor siguen en el puerto 8081 y no te llevan por error al Apache nativo.
  • Recursos: en la pestaña Red del navegador, recarga y revisa que no falten CSS, imágenes o JavaScript ni aparezcan errores inesperados. Si hay JavaScript, comprueba también su comportamiento y la consola.
  • Acceso directo: abre una página interior por su URL y recárgala. Solicita después una ruta inexistente y comprueba la respuesta 404.

Registra en tu Markdown una tabla breve con prueba, resultado en Apache nativo y resultado en el contenedor, las incidencias corregidas y capturas con la URL visible. Si esta versión es estática, verifica las funciones que ya tenía: todavía no estamos probando PHP ni acceso a datos.

Comprobar el comportamiento del contenedor

  1. Confirma que el portal funciona desde http://127.0.0.1:8081/ antes de continuar.
  2. Modifica un texto en estatica/index.html y recarga. Explica el papel del montaje.
  3. Desde Containers en Portainer, selecciona aea2-apache y utiliza Stop y después Start. Comprueba que cambia la disponibilidad, no el archivo original.
  4. Identifica imagen, nombre, puerto externo e interno. Conserva las pruebas antes de continuar.

Al terminar esta fase, libera el puerto para Compose:

sudo docker stop aea2-apache
sudo docker rm aea2-apache

Esta fase es el primer resultado que debes poder demostrar. Si hoy solo llegas aquí con la instalación documentada, continúa desde la fase 3 en la siguiente clase.

3. Preparar el entorno de cuatro servicios

  1. Revisa compose.yaml y relaciona web, php, db y java con la arquitectura. Localiza imágenes, Dockerfile, puertos, red, volumen y dependencias.
  2. Copia .env.example como .env. Genera tres claves distintas con openssl rand -hex 16 y completa DB_ROOT_PASSWORD, PHP_DB_PASSWORD y JAVA_DB_PASSWORD. No publiques estos valores.
  3. Revisa sql/: ya incluye creación y carga compatibles con el modelo, y el ajuste de cuentas. Se ejecuta solo en una base nueva. No lo mezcles con el directorio de datos de MariaDB instalado en Ubuntu.
  4. Comprueba que .env no se incorpora a Git y que 8081 y 8082 están libres.
cp .env.example .env
chmod 600 .env
sudo docker compose config --quiet

Edita .env antes de validar. Utilizamos config --quiet para validar sin volcar las contraseñas. Las cuentas se crean dentro del nuevo MariaDB, independientemente de las cuentas del servidor nativo.

4. Desplegar los servicios y entender sus conexiones

Servicio Acción Prueba
Base de datos sudo docker compose up --build -d db En ps, db pasa a healthy. Revisa logs y comprende el volumen y la carga inicial.
PHP-FPM y web sudo docker compose up --build -d web También arranca php por dependencia. En http://127.0.0.1:8081/ aparecen actividades y clasificación.
Java sudo docker compose up --build -d java http://127.0.0.1:8082/tornejos/ muestra rondas y permite registrar resultados. 
sudo docker compose ps
sudo docker compose logs web php db java

Explica las direcciones: navegador → 8081/8082 del ordenador; Apache → php:9000; PHP y Java → db:3306. No se publica 9000 ni 3306 al anfitrión. No uses localhost desde PHP para conectar con otro contenedor.

La configuración de Apache y FPM usa /var/www/html en ambas imágenes para localizar los scripts. La carpeta src queda fuera de la raíz pública. Tomcat recibe su configuración JNDI desde el entorno y el WAR sigue cerrado. El formulario PHP resultats.php permanece desactivado: los cambios se registran desde Java.

5. Pruebas de colaboración, persistencia y recuperación

  1. Demuestra los cuatro servicios y ambos portales. Si el volumen es nuevo, la partida 3 está pendiente y la clasificación inicial es Aina 3, Cris y Dani 1, Biel 0.
  2. Registra desde Java victoria B en la partida 3 y recarga PHP: Cris pasa a 4 puntos. Confirma que estás comparando los dos portales de contenedores, no uno nativo.
  3. Ejecuta sudo docker compose down y después sudo docker compose up -d. Comprueba que el resultado sigue guardado.
  4. Detén solo db mediante sudo docker compose stop db. Observa el fallo, consulta logs, recupérala con sudo docker compose start db y vuelve a probar.
  5. Comprueba que el MariaDB nativo no ha recibido estos cambios: son dos bases independientes. Explica dónde conserva sus datos cada una.

Conservar los datos

No utilices down -v ni prune para probar persistencia: pueden eliminar datos. Reiniciar tampoco vuelve a aplicar los SQL ni cambia automáticamente las contraseñas existentes.

Si editas código que se copia con COPY, reconstruye el servicio afectado. Para cambios compartidos en php/public, reconstruye web y php. No confundirlo con el montaje de carpeta de la fase estática.

6. Entrega y cierre

Capturas que deben acompañar tu Markdown individual

Numera las capturas y añade debajo una frase que explique qué has comprobado. Conserva las de la fase estática antes de retirar ese contenedor. No muestres contraseñas, archivos .env ni pantallas con variables de entorno.

  • Web estática: portal funcionando en el puerto 8081 y detalle de aea2-apache en Portainer, con imagen, estado y puertos.
  • Servicios: listado de Containers con web, php, db y java en ejecución. Portainer aparecerá además como contenedor de administración.
  • Conexiones: detalle de la red del proyecto donde se vean los cuatro servicios conectados, y detalle del volumen de MariaDB identificado con db. El volumen portainer_data pertenece a la interfaz, no a la base de datos.
  • Logs: registros de Apache después de visitar el portal, explicando una petición y su estado HTTP.
  • Funcionamiento y persistencia: resultado registrado desde Java y clasificación PHP actualizada, y la comprobación del mismo resultado después de recrear el entorno. Una captura de contenedores en ejecución no demuestra por sí sola que la aplicación funcione.

Puedes consultar estados, logs, redes y volúmenes desde Portainer. Mantén los comandos Compose indicados para construir y recrear el proyecto; no hace falta importar el YAML como un Stack de Portainer.

  • Repositorio del equipo con configuración, código y guía común de despliegue, sin .env ni contraseñas.
  • Markdown individual con instalación de Docker, versiones, diagrama, explicación de puertos/red/volumen, pruebas y una incidencia o decisión propia.
  • Demostración individual: web estática inicial y entorno completo colaborando, con persistencia comprobada.

La revisión utiliza los mismos bloques: trabajo en Git, MD individual, guía común, funcionamiento y explicación. Criterios principales: RA1 1.5, 1.6, 1.7, 1.8 y 1.9.
